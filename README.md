# LangGraph Research Assistant

Это мой личный учебный проект, в нем мы последовательно будем создавать агента с помощью langgraph, причем будем использовать широкие возможности langgraph такие как langgraph studio,
LangSmith, Langgraph dev server, langgraph SDK.

Примерный план разработки:

1. Создание общей арзитектуры агента
2. Запуск через Langgraph Server и исследование агентного графа через Langgraph Studio
3. Сохранение промптов, датасетов и создание экспериментов
4. Запуск агента в dev режиме через docker
5. Back end приложение и связь с агентным графом через langgraph sdk
6. Опционально: frontend на базе eopnwebui

## Общая архитектура агента

Сам агент представляет собой узел роутинга и несколько субагентов, выходящих из него. При этом разные субагенты имеют доступ к разным инструментам, определенным через @tool.
В этой работе для создания ReAct субагентов мы воспользовались функцией create_agent, чтобы не усложнять первичную архитектуру. 
Из важных вещей здесь стоит отметить 2:

- каждый инструмент представляет собой асинхронную корутину, чтобы мы имели возможность вызывать агент асинхронно
- в каждый узел агента помимо состояния передается runtime context

Последнее -- важный ньюанс, который раньше не применялся в моих работах. Context содержит в себе настройки графа, можно сказать, что это гиперпараметры графа.
С помощью Runtime[Context] мы сможем из Langgraph Studio запускать агента с различными системными промптами и на базе различных моделей, при этом не перекомпилировать граф и не перезапускать сервер.

## Запуск через Langgraph SErver

На сколько я понял, langgraph server автоматически создает REST API над скомпилированным графом, поднимает локальный сервер для запуска и отладки. Важно, что это именно Rest API самого графа, и по хорошему мы не должны отдавать его конечному пользователю в силу политики безопасности. Именно для этого в последствии мы соберем еще отдельное backend приложение, которое
уже будет публиковать ручки, которые будут доступны пользователю.

## Возможности langgraph studio

Здесь мы можем смотреть на визуализацию нашешл агентного графа, давать ему запросы, отслеживать его работу в интерактивном режиме. Здесь есть полная трассировка запросов, так что
не нужно запускать дополнительные сервисы вроде open telemerty или phoenix. Здесь можно посмотреть трассировку по компонентам, время исполнения каждого компонента, стоимость запроса.

Кроме того, здесь возможно сохранять и версионировать промпты, создавать свои датасеты и эксперименты. Примр файла с датасетом можно найти в репозитории. Этот файл можно просто загрузить в langgraph studio.

## Создание эксперимента

В каталоге с экспериментами мы написали простой эксперимент на оценку роутера на созданном датасете. Данный код является отдельным полноценным скриптом, который запускается локально, но
при запущенном langgraph dev. Это важно, поскольку скрипт тестирования использует laggraph client (можно сказать, что он использует langgraph sdk) для обращения к поднятому сервису 
langgraph server, в отличие от предыдущих подходов, когда мы тащили в тесты части исходного кода агента напрямую или через import соответствующих модулей.

Здесь стоит дать небольшое пояснение. Дело в том, что можно создавать эксперименты как самостоятельно через скрипты, так и через langgraph studio -- необходимо создать датасет, затем во
вкладке evaluators создать evaluator и запустить его на выбранном датасете. И в том и в другом случае система для тестирования будет использовать развернутый агентный граф, и в том и
в другом случае для тестирования будет использоваться указанный датасет, и в том и в другом случае метрики качества отобразятся в langgraph studio и их можно будет сравнивать. 
Вся разница здесь заключается в основном в том, какие цели в данный момент вы ставите перед собой.

В случае тестирования через скрипт, вам нужно будет писать его самостоятельно. В случае тестироавния через UI вам надо будет вручную настраивать evaluator и писать инструкцию для LLM-as-judge. 
Основное различие заключается в том, что через UI удобно проводить end-to-end тесты, когда необходимо прогнать весь граф и получить оценки работы агента в целом. Скриптом же можно
написать что-то вроде юнит-тестов, каждый из которых тестирует определенный компонент агента. Как в нашем случае -- мы написали скрипт тестирования только для компоента router.
Однако ничто не мешает вам писать end-to-end тесты также скриптами.

## Запуск агента в dev режиме в docker

Langgraph умеет самостоятельно поднимать готовый граф в продовом режиме в докере. Для этого он под капотом создает свой собственный docker-compose. В нем помимо самого langgraph server
будут так же базы данных postgresql и redis для персистентности памяти, хранения данных о сессиях и очереди сообщений. Сам docker-compose поднимается командой 
```
langgraph up
```
но можно также создать обычный Dockerfile
```
langgraph dockerfile Dockerfile
```
на базе которого выстраивать свои собственные сервисы и свой собственный docker-compose, если у вас, например есть какие-то дополнительные сервисы (backend, frontend, очередь сообщений и т д).
Краеугольным камнем является то, что langgraph обязательно требует наличия postgresql и redis, поскольку эти инструменты прибиты в исходном коде библиотеки гвоздями. Так что,
если вы выстраиваете свой собственный сервис, то вам необходимо определить postgresql и redis в своем docker-compose. Хорошая новость в том, что в переменных окружения сервиса langgraph server вы можете указать, на каких хостах и портах определены ваши postgresql и redis.

Различия между dev и up. Первый режим langgraph server -- отладочный, второй как бы прод. Отладочный вариант использует один локальный python процесс, который поднимает сервер
на локальном хосте и не имеет персистентной памяти (все InMemorySaver) и очереди задач. Зато он имеет hot reload, то есть при изменении кода сервер автоматически презагружается (как в fast api).
В случае, когда мы разворачиваем langgraph server через docker у нас появляется долговременная персистентная память и очередь сообщений за счет postgresql и redis, но мы платим за это
отсутствием hot reload.

## Backend приложение

Когда мы запускаем langgraph server в prod режиме langgraph studio открывается через браузерный UI
```
https://smith.langchain.com/studio/?baseUrl=http://localhost:8123
```

Последним завершающим шагом создания приложения является fast api backend. Langgraph server предоставляет полный REST API для агентного графа, но его нельзя использовать в качестве
полноценного backend, так как многие возможности там дают доступ напрямую в внутреннему состоянию агента. С точки зрения безопасности, нельзя предоставлять эти возможности пользоваетлю,
поэтому необходимо дополнительно сделать отдельный backend, который будет давать прльзователю только ограниченный набор ручек. Далее этот backend так же можно связать с фронтэндом, 
например на базе openwebui. 
Обратим внимание, что backend связывается с агентом не на прямую, а через langgraph sdk. Другими словами, fast api backend и langgraph server являются двумя независимыми сервисами,
которые общаются через langgraph sdk. В других случаях backend мог бы обращаться напрямую к функциям агента, таким как graph.ainvoke и др, здесь же между fast api backend и агентом
есть API прослойка в виде langgraph server. Такой подход позволяет с одной стороны разрабатывать backend и агентную часть еще более независимо, так как backend привязывается к 
langgraph sdk, который гарантируется фреймворком, а не к функциям агента, с другой стороны позволяет проводить тестирование, исследование и отладку агентного графа в отрыве от backend.

Обратим также внимание на то, что в данном случае, мы предполагаем, что backend разработчики захотят ввести очередь сообщений rabbitmq для backend. При этом у нас уже есть redis, который
выполняет функцию очереди в langgraph server. В данном случае, эти 2 очереди никак не конфликтуют друг с другом. Если рассмотреть langgraph server и fast api backend как 2 отдельных микросервиса, которые общаются между собой черех REST API, то redis управляет задачами только в рамках langgraph server, а rabbitmq в рамках всего остального bckend.

## Подготовка к запуску

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e .
cp .env.example .env   # затем впишите ключи
```

```bash
langgraph dev
```

Поднимет LangGraph Server на `http://127.0.0.1:2024` и откроет LangGraph Studio.
Граф будет доступен под именем `research_assistant` (см. `langgraph.json`).

## Backend и полный стек в docker-compose

Это шаг 5 плана: над графом появляется собственное FastAPI-приложение, которое
общается с LangGraph Server **по сети через langgraph-sdk** (а не импортирует код
графа). Наружу мы публикуем только backend; «голый» REST API графа остаётся
внутри docker-сети.

`docker-compose.yml` поднимает шесть сервисов:

- **postgres**, **redis** — обязательные для прод-режима LangGraph Server
  (персистентность чекпоинтов и его внутренняя очередь run-ов). Адреса задаются
  переменными окружения `DATABASE_URI` и `REDIS_URI` сервиса `langgraph-server`.
- **rabbitmq** — прикладная очередь сообщений, связанная с backend.
- **langgraph-server** — собирается из `Dockerfile` (сгенерирован
  `langgraph dockerfile`).
- **backend-builder** — отдельный контейнер-сборщик: единственная задача —
  выполнить `uv sync`, сложить готовое виртуальное окружение в том `backend-venv`
  и завершиться. `backend` и `worker` ждут его (`service_completed_successfully`)
  и запускаются на уже готовом окружении (`uv run --no-sync`), ничего не собирая.
- **backend** (FastAPI) и **worker** — используют один и тот же образ `uv` и общий
  venv-том.

### Как RabbitMQ уживается с Redis у LangGraph Server

Это два РАЗНЫХ слоя очередей, они не конфликтуют:

- **Redis у LangGraph Server** — его *внутренняя* очередь задач. Создаём run через
  SDK — сервер кладёт его в Redis, а воркеры внутри контейнера `langgraph-api`
  разбирают. Этот механизм «прибит гвоздями» в библиотеке, заменить его на
  RabbitMQ нельзя и не нужно.
- **RabbitMQ у backend** — очередь *прикладного* уровня. Она развязывает HTTP-ручку
  от тяжёлой работы: ручка публикует задачу и сразу отдаёт `job_id`, а отдельный
  `worker` забирает её из RabbitMQ и уже сам идёт в LangGraph Server через SDK.

Иначе говоря, RabbitMQ живёт «над» LangGraph, а Redis — «внутри» него; мостом
между ними служит `worker`. Чтобы прикладные данные не пересекались с внутренней
очередью LangGraph, backend хранит статусы задач в отдельной логической БД Redis
(`/1`).

### Запуск

```bash
cp .env.example .env   # впишите LLM_* и LANGSMITH_API_KEY (их подхватит compose)
docker compose up --build
```

- Backend (Swagger): `http://localhost:8000/docs`
- RabbitMQ (консоль, guest/guest): `http://localhost:15672`
- REST API графа (для отладки): `http://localhost:8123`

### Ручки backend

```bash
# Синхронно: backend сам ждёт граф через SDK
curl -X POST localhost:8000/chat -H 'Content-Type: application/json' \
  -d '{"message": "Найди свежие статьи про retrieval-augmented generation"}'

# Асинхронно: задача → RabbitMQ → worker → LangGraph
curl -X POST localhost:8000/chat/async -H 'Content-Type: application/json' \
  -d '{"message": "Сделай конспект статьи 1706.03762"}'
# → {"job_id": "...", "status": "queued"}

curl localhost:8000/jobs/<job_id>   # статус/результат
```
